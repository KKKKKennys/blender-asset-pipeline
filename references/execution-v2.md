# V2 执行约定

## 最小任务记录

沿用用户已经确定的格式和授权。只在缺少真正影响结果的输入时询问，不重复索取已确认信息。每次操作前记录模式、工程副本、对象范围、命名规则和导出目标；小任务可用一张表。

JSON 计划的 `schema_version` 为 `2.0`。`scope_ids` 是本次任务中确定的对象/数据块身份，不使用会被修改的名称当作唯一身份。读取现场后建立映射；是否写入自定义 UUID 必须在修改范围内，纯检查不写自定义属性。

- `mode`: `audit`、`organize`、`export`、`organize_export`。
- `renames`: `id / namespace / old / new`；名字按 Blender 各数据块命名空间精确比较。
- `occupied_names`: 批次内外当前已占用的 `{namespace, name}`，不能省略批次外冲突检查。
- `exports`: `id / path / overwrite_approved`；`path` 相对任务交付目录。
- `existing_files`: 输出目录中已有相对路径。
- `case_sensitive_paths`: 布尔值，依据实际目标文件系统配置；默认 false，便于 Windows 交付。

输出路径与 `existing_files` 采用相同的词法规范化：统一正反斜杠、折叠重复分隔符与 `.`，再按大小写策略比较。路径必须指向交付目录内的文件，不能是目录本身或含 `..`。`overwrite_approved` 必须为布尔值，只有 `true` 表示已声明覆盖授权。该检查不访问文件系统，也不解析符号链接或文件系统特有的别名，执行前仍需核对真实目标。

完整虚构样例见 [计划示例](../examples/organize-export-plan.json)。

## 检查计划

任务产生了批量改名或导出计划时，运行 `python scripts/check_plan.py <计划文件>`。退出 0 为计划一致，退出 1 为需修订；普通文字咨询无需生成 JSON。

该工具只验证模式、范围 ID、目标重名、已占用名称、路径与覆盖声明。它不检查真实对象引用、共享 datablock、外部库和材质，也不证明用户实际上授权过 `overwrite_approved`。这些必须由 Agent 根据现场与对话核对。

## 执行与恢复

1. 冻结已选范围与规则摘要，对照工程是否在检查后又发生变化；有变化时重建受影响部分的计划。
2. 对执行结果逐项记录 `planned / done / failed / skipped`。同一对象或文件不要因后续成功而覆盖前面的失败记录。
3. 交换名字使用临时唯一名；保留原名映射。无法保证字符串引用或库链接安全时只跳过对应项，不扩展修改范围。
4. 中断后核对当前工程、规则版本、目标路径和已完成项。只有证据一致的 `done` 项可以跳过；其他项重新检查，避免从头重复改名。
5. 导出写入当前任务的独立目录。允许覆盖时也保留被替换文件的备份；改变选择、模式、活动场景的临时状态在 finally 中恢复。

## 分层验收

`generated`：文件存在且格式可读；`reimport`：在隔离场景回读并核对数量、尺寸、材质和纹理；`visual`：画面或实际目标软件中确认外观。每层使用 `not_run / passed / failed / blocked`，并附证据路径。未执行的检查保持 `not_run`。

不要以文件大小、脚本退出码或计划检查器通过替代回读与外观验收。
